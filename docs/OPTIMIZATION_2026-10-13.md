# TX2 部署与响应性能优化：v0.3.0 实测报告

日期：2026-10-13。相机：DS-2DC2402IW-DE3 S6。阶段：部署和性能优化，人员跟随现场复验等待用户配合。

## 完成范围

本轮保留 YOLO26n 的模型权重、320×320 输入和 NCNN CPU FP32 推理方式，改进运行时线程配置、取帧与控制流程。
视频解码继续使用 TX2 的硬件解码器；**硬件视频解码不等于模型 GPU 推理**，本轮没有实现 TensorRT、CUDA 或 Vulkan 模型加速。
板子此前已处于 MAXN。本轮没有修改功耗档位、锁频、提高相机编码帧率或改写相机码流配置。

部署在独立目录 `/home/nvidia/tx2-ptz-optimized-20261013/jetson-ptz-inspection`，保留旧工程和 v0.2.0 ZIP 供回退。
网页：`http://192.168.1.4:8770/`。报告取证时为观察模式，`enabled=false`、`calibrating=false`，没有启用云台跟随。
**本轮非零运动指令为 0。短脉冲是否能有效驱动这台云台、回中是否更快，均未做机械实测。**

## 优化后的链路

```text
相机既有码流 → RTSP TCP → GStreamer 硬件解码、缩放 1280×720
  → RTSP 工作进程及其线程限制在 CPU 0,3,4,5
  → JPEG 输出上限 20fps → 后台只保存最新帧
  → 取最新未消费帧 → NCNN 2 线程、CPU 1,2、OpenCV 1 线程
  → 平时跳过校准光流 → YOLO26n 检测 → 浏览器刷新检测 JPEG
  → 仅在用户启用并重新标定后：有界自适应脉冲 → STOP → 等待 → 取停止后的新帧
```

1. **线程与亲和性**：离线测量 6 组配置后，CPU 1、2 的两个 Denver 核、NCNN 两线程、OpenCV 一线程取得最小 IPC P95；最终生产配置依据后续连续流检查决定。线程更多没有保证更快。此 CPU 编号针对本台 TX2，不能作为其他板子的通用配置。
2. **校准光流按需计算**：原流程每帧都计算背景光流。新版平时仅做检测，在校准时请求光流，并清除不连续的光流历史，避免把切换后的帧错误关联。
3. **最新帧策略**：观察及跟随读取最新未消费帧，跳过中间积压；标定仍要求新鲜帧。动作完成并停止、等待后设置接收时间屏障，下一次检测使用屏障之后收到的图像。
4. **自适应步长**：保持单轴、速度指令 ±20，按照标定矩阵和死区外误差估算动作时长，限制 100～500ms。接近中心时缩短脉冲，不是 PID，也没有积分或微分项。标定仍使用 500ms。
5. **处理时序**：普通动作的等待与动作时长相关，额外停止后等待保持；检测循环间隔为 20ms。该间隔不是推理帧率，也不代表电机每 20ms 可完成响应。
6. **协议兼容**：JPEG 长度头高位表示本次跳过光流，旧长度请求仍走原路径。新增协议边界及优化流程测试，保持失败、超时、陈旧图像、重连、停止指令异常时禁用控制的行为。
7. **采集与检测核隔离**：新增 `rtsp_cpus` 配置，RTSP 子进程通过 taskset 启动，其新线程继承允许 CPU 集合。
   本台将 RTSP 工作进程限制在 A57 的 0、3、4、5 核，将检测器限制在 Denver 的 1、2 核，避免采集热点线程占用推理核。
   未设置该配置时保留原有调度行为，不能照搬到 CPU 拓扑不同的硬件。

## 计时口径

全部时间为本台 TX2 单调时钟统计，表格单位 ms，单元格为“中位数 / P95”。

- `network_ms`：仅 NCNN 网络前向计算。
- `inference_ms`：为兼容旧字段，表示预处理加网络推理，不是纯网络耗时。
- `flow_ms`：背景光流阶段；跳过时接近零，仍有计时开销。
- `total_process_ms`：JPEG 解码至预览编码完成，不包括等待输入和 IPC 输出。
- 离线 `wall_ms`：完整一轮 IPC 请求耗时。
- 连续流 `pipeline_ms`：本次取帧开始至处理结果生成，包括等待帧及处理。
- `decoded_frame_age_ms`：JPEG 到达 TX2 后至结果生成的时间，可能包含已经在最新帧缓存中等待的时间。

**没有测量相机曝光至浏览器显示的端到端延迟，也没有测量云台机械响应。收帧龄不是现场延迟。**

## 离线性能对照

使用两张固定 JPEG，每个模式预热 6 次、统计 30 次；每组包含两张图像的结果。图片保留本地，不收入公共工程包。

| 配置 / 模式 | CPU | NCNN线程 | OpenCV线程 | 预处理＋推理 | 光流 | IPC整轮 |
|---|---|---:|---|---:|---:|---:|
| legacy-4-auto / legacy | 不绑核 | 4 | OpenCV 默认 | 97.251 / 103.232 | 36.686 / 42.765 | 170.395 / 179.257 |
| legacy-4-auto / light | 不绑核 | 4 | OpenCV 默认 | 86.910 / 95.026 | 0.001 / 0.001 | 126.077 / 131.174 |
| light-4-cv1 / light | 不绑核 | 4 | 1 | 89.355 / 98.407 | 0.001 / 0.001 | 130.750 / 141.424 |
| light-3-cv1 / light | 不绑核 | 3 | 1 | 111.076 / 116.572 | 0.001 / 0.001 | 151.340 / 158.086 |
| light-2-cv1 / light | 不绑核 | 2 | 1 | 128.397 / 141.789 | 0.001 / 0.001 | 168.226 / 182.657 |
| light-2-denver / light | 1,2 | 2 | 1 | 71.073 / 82.266 | 0.001 / 0.001 | 110.402 / 121.857 |
| light-4-a57 / light | 0,3,4,5 | 4 | 1 | 78.500 / 79.264 | 0.000 / 0.001 | 123.287 / 126.031 |

原配置到所选配置，离线预处理＋推理中位数由 97.251ms 降至 71.073ms，减少 26.9%；
JPEG 解码至预览编码完成由 169.391ms 降至 109.489ms，减少 35.4%。
这包含运行时配置和跳过光流的共同作用，不能把全部改善归因于模型网络。

所有配置在这两张固定图上的人员框坐标和置信度最大差异均为 0；权重 SHA256 校验通过。
这是同输入一致性检查，**不是数据集 mAP、召回率或精度不下降的证明**；没有改变权重或输入尺寸也不替代业务精度评估。

## 相机连续视频流对照

三组在同一相机上按顺序运行，每组预热 6 帧后统计 40 帧。场景可能随时间改变，不能作为严格同帧精度对比。
baseline-v02 复现 4 线程、不绑核、每帧光流、fresh 取帧；两组优化使用所选线程配置、按需光流、latest 取帧。
`rtsp_fps` 是解码后 JPEG 输出上限，不是相机编码帧率，也不是 YOLO 检测帧率。

| 组别 | JPEG输出上限fps | 预处理＋推理 | 光流 | 检测器处理 | 取帧到结果 | 收帧至结果 |
|---|---:|---:|---:|---:|---:|---:|
| baseline-v02 | 10 | 114.956 / 140.862 | 32.539 / 50.342 | 201.602 / 228.392 | 291.250 / 427.945 | 203.350 / 230.310 |
| optimized-10fps | 10 | 256.658 / 269.410 | 0.001 / 0.001 | 295.043 / 306.853 | 296.850 / 308.615 | 361.700 / 497.070 |
| optimized-20fps | 20 | 70.245 / 76.356 | 0.001 / 0.001 | 107.613 / 114.971 | 108.900 / 127.755 | 129.550 / 201.230 |

这三组短时测试选择 **optimized-20fps / 20fps**。相对本轮 baseline-v02，取帧到结果中位数减少 62.6%，
P95 减少 70.1%；预处理＋推理中位数减少 38.9%。

本次 optimized-10fps 的流水线中位数高于 baseline-v02，且检测与收帧龄数据明显退化。因此不能把离线最优配置直接等同于连续流最优，也不能声称所有优化组都变快。本次短时对照保留 20fps 的通过数据，但其随后生产运行也出现退化。后续同进程调度 A/B 获得了 RTSP 工作线程与检测器争用 Denver 核的证据，详见下一节。这不证明采集帧率对性能具有独立因果关系。

不同帧率组的性能差异不能证明“增加输出帧率一定缩短推理耗时”。所选结果是当前软硬件和现场画面下的有限样本，
没有长时间温升、多人复杂场景或多日稳态性能保证；后续应在保持场景与温度条件尽量一致时重复测试。

## 生产退化的诊断与调度 A/B

短时 optimized-20fps 通过后，原生产服务的推理再次变慢。诊断采样 8 次，
纯网络推理为 246.474～255.775ms。
CPU 1、2 的所观测频率为 2035200kHz；诊断仅发现一个检测器进程。
RTSP 工作进程主线程在这些采样中最近运行于 CPU 1，而检测器线程最近运行于 CPU 2。
原 RTSP 线程允许使用全部六个核，与仅能在 1、2 核执行的检测器共享计算资源。
这些是有限采样的调度和频率事实，不能替代连续的调度追踪，也不能据此排除所有瞬时降频或其他系统影响。

随后在**同一存活的检测器和 RTSP 工作进程、不重启程序、不改变模型或功耗**的条件下做可逆 A/B：
先测原 RTSP 允许全部 CPU 的状态，再仅把该工作进程当时存在的全部线程限制到 A57 0、3、4、5 核，
等待后再测；两段脚本各取样约 25 秒，按处理帧序号保留不同检测帧。实验结束还原原亲和性。

| 调度组 | 不同检测帧样本数 | 纯网络推理 | 取帧到结果 | 收帧至结果 |
|---|---:|---:|---:|---:|
| denver-with-unrestricted-rtsp | 82 | 246.385 / 249.949 | 286.950 / 290.995 | 311.950 / 392.950 |
| denver-with-a57-rtsp | 189 | 66.010 / 72.269 | 109.500 / 124.160 | 133.900 / 186.120 |

仅调整 RTSP 工作线程允许的 CPU 后，纯网络推理中位数减少 73.2%，
取帧到结果中位数减少 61.8%。这提供了采集热点线程与 Denver 推理核争用、
核隔离能缓解本次退化的直接对照证据。未改变相机输出或模型，不应把改善归因于增加视频帧率。
原始 10fps 与 20fps 对比的独立因果关系仍未验证，不能声称帧率越高推理越快。
这个 A/B 实验只是约 50 秒的连续观察；最终部署再做下面的取样检查，长期和多场景表现仍待验证。

## 实机验证与部署状态

最终部署选择 `optimized-denver2-a57capture-20fps`，记录的依据：同一存活进程的亲和性对照显示，限制视频采集核可缓解与检测器的 CPU 争用；最终部署的连续观察指标独立保存在 web-check.json。
最终模板及实际服务互相核对：JPEG 输出上限 20fps、NCNN 2 线程、
CPU `1,2`、OpenCV 1 线程。离线最优、短时连续流最优与生产配置是三个不同结论；
最终 RTSP 工作进程 CPU 配置为 `0,3,4,5`。
上面的短时改善比例不能直接作为生产稳态改善比例。

TX2 板端 104 项测试通过；独立目录 C++ 检测器及图像推理程序编译完成；模型哈希验证通过。
网页预览取样通过，最近预览 JPEG 为 71726 字节。在 90.031 秒中取样 464 次，
处理帧计数增加 682、解码帧计数增加 1804，应用处理约 7.575 帧/秒；源重启次数为 0。

## 待现场复验

用户已明确本轮先做部署和性能优化，稍后测试跟随。因此当前暂停的是需要人员走动与云台运动的实验，不影响已完成的软件检查。

1. 在固定安装和正常画面方向下重新校准，核实 100～500ms 脉冲的有效性和位移关系。
2. 从相同起始偏差比较 fixed 与 adaptive 的回中时间、超调、动作次数和稳定死区。
3. 站定后检查抖动，再缓慢左右移动，验证跟随、目标丢失 STOP 和恢复行为。
4. 采集精度样本，验证不同距离、光照和目标大小。仪表模型、逐表扫描、对焦、读数与上传仍需后续对接。

本报告记录了短时对照中的改善及最终部署取样，并已实现缩短动作时长的策略。
不能据此保证长时间推理始终更快，也不能声称云台机械响应或动态追踪已经验收。
