# 追踪响应优先优化：v0.4.0 工程验证

日期：2026-10-13。设备：Jetson TX2＋海康 DS-2DC2402IW-DE3 S6。
本轮优先解决运动时检测被串行等待阻塞、实时画面随检测更新变慢的问题。
**物理相机非零运动指令为 0；实时视频与检测在实机运行，运动调度使用 FakeMotion 验证。**

## 结论及验证边界

软件已增加独立运动工作线程、按需检测预览和独立 MJPEG 实时画面。
检测不再等待整次跟随运动与停稳周期结束；运动期间的新检测结果可以触发回中、目标丢失或方向变化时的取消。
当前仍为 NCNN CPU FP32、320×320 输入，未换权重、未实现 GPU 推理或 PID。
本轮实测指标分别报告检测完成间隔、模拟运动窗口内完成检测次数、MJPEG 接收帧率与应用处理帧率。
**这些指标不是相机曝光至浏览器显示的端到端延迟，也不是云台电机机械响应或实际动态追踪验收。**

## 架构变化

```text
相机 → RTSP → 独立解码采集工作进程 → 最新源JPEG
              ├─ 检测循环 → NCNN → 最新目标位置
              │                  └─ 单个运动工作线程 → 短脉冲 → STOP → 停稳
              │                      ↑ 丢失、回中、反向或旧帧可取消
              ├─ MJPEG实时预览 → 浏览器实时画面（不等检测或运动）
              └─ 按需检测预览 → 同帧JPEG与同帧检测框 → 浏览器检测画面
```

| 路径 | v0.3及此前 | v0.4实现 |
|---|---|---|
| 跟随运动 | 主检测循环内运动、停止、等待，检测随之暂停 | 单个独立运动工作线程，检测继续 |
| 动作请求 | 每轮按当前检测执行一次 | 保留最新反馈，不排队、不重叠启动动作 |
| 追踪脉冲 | 自适应100～500ms | 本模板限制100～200ms，指令速度仍为±20 |
| 校准 | 同步500ms脉冲 | 保留原同步500ms，不套用跟随上限 |
| 检测预览 | 每个检测结果都编码预览 | 用户请求检测画面时最多按0.35s间隔生成 |
| 实时画面 | 显示处理后的检测JPEG，随推理及运动节奏刷新 | 直接显示采集源JPEG组成的MJPEG，不等待推理 |

实际跟随仍需重新校准。暂停、丢失、回中、方向或轴变化、帧过期时取消旧动作，递增控制代数并发送 STOP。
新动作等旧工作线程停止及120ms等待完成后才可启动，避免取消过程中追加反向指令。
提交与实际发指令前均检查本地 JPEG 接收时间，超过0.5s不发运动；停止后的新动作还需通过收帧时间屏障。
这里的0.5s是本地接收帧龄界限，不能证明相机编码或网络内部延迟小于0.5s。

## 检测与显示分离

检测器的IPC长度头保留旧协议，bit31表示跳过校准光流，bit30表示跳过可选预览。
跳过预览仍输出检测结果，但不画框、不编码预览JPEG，降低控制路径额外工作量。
请求检测预览时，服务保存这张JPEG对应的检测结果和帧号；网页只用该预览的检测框，避免新框叠到旧图上。
原始实时MJPEG不叠加异步检测框，通过网页CSS处理旋转，目标框在检测画面查看。

`/api/live.mjpeg` 每个客户端使用独立源序号，不推进检测器的读取序号；不为慢客户端建立帧队列。
最多两个客户端，每个完整multipart帧写入有1s总操作超时，超额客户端返回429；断线释放客户端名额。
这些约束验证软件资源和超时行为，没有把MJPEG视为音视频编码码流或WebRTC。

本轮尝试过`videorate drop-only=true`。该选项的含义是仅丢帧、不复制帧，见
[GStreamer官方说明](https://gstreamer.freedesktop.org/documentation/videorate/index.html)。
实际旧版OMX解码器出现`not-negotiated`，未输出JPEG；恢复原普通videorate后输出正常，
对照保存在`source-diagnostic.json`。最终工程已撤回该选项，保留原已验证采集参数。
设置20fps是解码后JPEG输出目标；相机码流帧率、JPEG输出率、检测率、MJPEG接收率和浏览器渲染率是不同指标。

## 检测器预览开销对照

板端同一组固定JPEG，模型、输入尺寸与线程配置保持相同；每组预热6次、统计20次。
所有单位ms，单元格为中位数 / P95。`light`关闭光流但生成检测预览，`light-no-preview`同时跳过光流和预览。

| 模式 | 样本数 | 纯网络推理 | 检测结果完成 | 预览阶段 | 解码至处理完成 | IPC整轮 |
|---|---:|---:|---:|---:|---:|---:|
| light | 20 | 74.418 / 78.235 | 87.659 / 93.524 | 27.045 / 29.022 | 114.776 / 119.184 | 115.610 / 120.190 |
| light-no-preview | 20 | 69.805 / 78.733 | 81.210 / 90.162 | 0.000 / 0.000 | 81.210 / 90.162 | 81.864 / 90.792 |

跳过预览后，检测器处理完成中位数减少29.2%。
`control_result_ms`从JPEG解码计时开始至检测后处理完成，不包括之后预览生成；
`total_process_ms`包含可选预览，`wall_ms`包含完整IPC交换。
`inference_ms`仍是预处理加网络前向，纯网络指标为`network_ms`。
这些字段不能混用，也不能把跳过预览节约的时间当作神经网络加速。

同一JPEG在所有协议标志组合下的人员框与置信度保持容差内一致，光流历史重置与零长度预览包边界检查通过。
这是同输入一致性验证，未测数据集mAP、召回率或仪表业务精度。

## 运动调度验证：真实采集和推理＋FakeMotion

实时相机RTSP及NCNN实际运行，运动接口替换为FakeMotion，模拟的MOVE与STOP不会发往真实相机。
串行和responsive采用相同200ms脉冲条件对照，避免把不同脉冲长度误认为调度优化收益。
调度输入范围：固定合成目标框与合成标定矩阵；真实图像仍完成NCNN检测，但其人员位置不驱动本次模拟动作。

| 模式 | 观察时长s | 检测完成数 | 检测完成间隔中位数/P95 ms | 模拟动作数 | 模拟运动窗口内完成检测数 | 检测fps |
|---|---:|---:|---:|---:|---:|---:|
| serial | 12.000 | 22 | 528.881 / 596.630 | 22 | 0 | 1.833 |
| responsive | 12.000 | 103 | 107.775 / 155.704 | 22 | 41 | 8.583 |

responsive的检测完成间隔中位数减少79.6%；串行模式模拟运动期间没有新检测完成，responsive在模拟运动窗口内完成41次新检测。
运动窗口从模拟MOVE至模拟STOP，包含软件等待，不表示物理电机在这段时间实际转动。
运动窗口内的检测完成数用于说明检测与动作可并行，不能作为人体追踪成功率。
FakeMotion的函数返回时间不包含真实ISAPI网络交换、电机惯性、机械起步或相机自动对焦，不能代替现场响应测试。
